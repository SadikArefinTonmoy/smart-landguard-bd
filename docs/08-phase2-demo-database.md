# Phase 2: PostgreSQL-based DEMO Registry / Privacy Architecture

## Design constraints

- Synthetic registry rows have IDs `DEMO-LR-*`, synthetic owners, invented khatian and dag values, `is_demo=1` enforced by DB check. **No government API**. A demo match is merely comparing text with invented data; cannot establish legal title or authenticity.
- All user-visible registry content is marked demo. Public demo listings retain their original sample content; authenticated demo registry stores new sample records in PostgreSQL.
- PostgreSQL remains local-only (`127.0.0.1:5432`) and Flask remains local-only (`127.0.0.1:8000`). Random credentials generated by `scripts/setup_local.py`, and `.env` ignored.
- Passwords use Argon2id. Sessions are random, hashed in DB and stored only in HttpOnly browser cookie with CSRF challenge. Buyer registration does **not** verify email/phone/identity. Administrator and Seller are provisioned by local CLI only.
- `land_records` and `registry_checks` store fictional record metadata and access-scoped check results. Registry check history is **only visible to the session owner**.
- `private_documents` holds metadata (filename, size, SHA-256, owner ID, opaque encrypted filename), **not raw files**; Fernet-encrypted documents live at `backend/instance/encrypted_documents/`. This is a development-only vault; use KMS/managed object storage for a real application.
- Permission model: owner can access their file; another logged-in account only through 24h grant, revocable by owner. Admin role alone grants no file access. Every file download enforces access on the server. User can delete own file; encrypted file and permissions are removed.
- Upload length, extension, magic-header and DOCX envelope are validated but **there is NO malware scanner**. Limit 10 files/account; no real documents permitted.
- Metadata audit records login, failed requests, registry changes and file actions. Audit logs record neither plaintext credentials nor document bytes.
- Manual privacy request intake remains: request recording is NOT equal to fulfilled deletion. Additional DSR tooling needed before real deployment.

## Schema

The live demo schema in `backend/migrations/002_postgresql_demo_active.sql` is idempotently applied at startup by `app.database.initialize()` for an empty demo database. Core tables: `users`, `sessions`, `login_attempts`, `audit_events`, `verification_events`, `privacy_requests`, `land_records`, `private_documents`, `document_grants`, `registry_checks`. Existing `001_*_OLD_DESIGN_ONLY.sql` is retained for historical explanation and **is not executed**.

The current schema uses TEXT-based UTC timestamps for compatibility with the previous Phase 1 prototype and does not implement hardened production migration management or PostgreSQL RLS. A production schema should use `timestamptz`, migrations, restricted DB roles, audited data minimization and strong key management.

## API surface (local only)

- `POST /api/auth/register`: Buyer **demo** registration, with CSRF; admin cannot self-register.
- `GET /api/demo-registry`: Login; lists up to 30 synthetic records; `q` searches locally.
- `GET /api/demo-registry/:id`: Login; single fictional record.
- `POST /api/demo-registry/check`: Login, CSRF; compares user-supplied demo text with a chosen record, saves owner-scoped history.
- `GET /api/demo-registry/history`: Login; own recent checks only.
- `POST /api/demo-registry/admin`, `DELETE /api/demo-registry/admin/:id`: Admin, CSRF; add and disable fictional records.
- `GET /api/demo-admin/summary`: Admin; counts only.
- `GET /api/documents`: Login; own and explicitly shared demo file metadata only.
- `POST /api/documents`: Login, CSRF; explicit demo/authority flags and encrypted storage.
- `GET /api/documents/:id/download`: Login; owner/grant only, attachment download.
- `DELETE /api/documents/:id`: Login+CSRF; owner only.
- `POST/DELETE /api/documents/:id/grant`: Login+CSRF; owner only, grant for 24h or revoke.
- Existing verification, dashboard, moderation, original listings/reports and privacy endpoints remain intact.

## Pre-launch blockers

Government authorization/data sharing; verified account identity and owner consent; privacy law review; safe PDF/DOCX preview and malware sandbox; independent security audit and penetration testing; encryption-key lifecycle and per-file envelope keys; backup/restore and disaster recovery; account recovery, email validation, OTP; CSRF/session/origin/TLS/reverse-proxy review; production PostgreSQL isolation and RLS; complete deletion/retention policy; logging policy, monitoring and incident response. **No one should use this prototype to make property purchase decisions.**
